# AdCoin Reverse Engineering — отчёт №22: прогресс этапов 1–21 и продолжение анализа

**Дата:** 2026-11-26  
**Основа:** `AdReverseEngineering-main(1).zip`, существующие материалы `reports/`, Smali-код APK и сетевые дампы `all-traffic(1..3).mitm`.

> Важно: в архиве нет единого журнала с исходной нумерацией всех 21 этапа. Таблица ниже — восстановленная по существующим отчётам последовательность направлений и результатов. Она не выдаётся за дословный первоначальный план.

## 1. Краткий итог

Работа продвинулась значительно в исследовании **клиентской части** AdCoin: разобраны основные API баланса, цепочки обновления состояния, AppLovin MAX reward flow и несколько offerwall-интеграций. В сетевых дампах найдены два воспроизводимых наблюдения увеличения баланса на `+0.69` после rewarded-video циклов.

При этом **окончательный серверный механизм начисления пока не установлен**. Не найдено доказательство, какой конкретно сигнал является условием начисления на backend AdCoin: AppLovin S2S callback, Axon completion event, другой серверный postback или сочетание нескольких событий.

Оценка прогресса:

- Клиентский API и модель баланса: **высокая степень определённости**.
- Локальный MAX callback: **высокая степень определённости**.
- Сопоставление событий просмотра и изменения баланса: **хорошая наблюдательная база, но причинность не доказана**.
- Серверная точка принятия решения о начислении: **не установлена**.

## 3. Продолжение анализа: `dailyTargetPartnerCode`, `adBonusDays` и PartnerResponse

### 3.1. Точное соответствие полей `UpdateDataResponse`

В `bbb.smali` сериализатор `UpdateDataResponse` содержит девять полей в следующем порядке:

1. `cash`
2. `series`
3. `adBonusDays`
4. `dailyTargetNeedProgress`
5. `dailyTargetProgress`
6. `dailyTargetReward`
7. `dailyTargetDescription`
8. `dailyTargetIsChangeAvailable`
9. `dailyTargetPartnerCode`

В `dbb.smali` это соответствует полям модели:

| Поле модели | JSON-поле | Тип |
|---|---|---|
| `dbb.a` | `cash` | `double` |
| `dbb.b` | `series` | `int` |
| `dbb.c` | `adBonusDays` | `int` |
| `dbb.d` | `dailyTargetNeedProgress` | `int` |
| `dbb.e` | `dailyTargetProgress` | `int` |
| `dbb.f` | `dailyTargetReward` | `int` |
| `dbb.g` | `dailyTargetDescription` | `String` |
| `dbb.h` | `dailyTargetIsChangeAvailable` | `boolean` |
| `dbb.i` | `dailyTargetPartnerCode` | `String` |

### 3.2. Что клиент делает с этими значениями

В `xn3.smali` после получения `UpdateDataResponse`:

- `dbb.c` передаётся в `g70.p(I)` — отдельное состояние, соответствующее `adBonusDays`;
- `dbb.a` записывается в `g70.D` — локальное значение баланса;
- `dbb.b` передаётся в `g70.r(I)`;
- поля `dbb.e`, `dbb.d`, `dbb.i`, `dbb.h`, `dbb.g`, `dbb.f` передаются в объект `lo2`, используемый состоянием интерфейса ежедневной цели.

Следовательно, `dailyTargetPartnerCode` (`dbb.i`) в найденной клиентской цепочке используется как часть состояния daily-target UI. В исследованном call path он **не передаётся в AppLovin callback и не участвует в локальной записи `cash`**.

Это не исключает серверного значения данного поля: backend может использовать его для маршрутизации/учёта партнёра. Но из клиентского кода такого назначения доказать нельзя.

### 3.3. PartnerResponse и `/adcoin/partners/get/{...}`

В `s00.smali` найден запрос `adcoin/partners/get/`. Ответ декодируется как `List<PartnerResponse>`.

Сериализатор `t48.smali` и модель `v48.smali` показывают, что `PartnerResponse` содержит ровно два поля:

- `code: String`
- `bonus: Int`

Далее `xn3.smali` преобразует элементы списка в UI-модель `o48`. В преобразовании код партнёра сохраняется, а из строки кода дополнительно вычисляются параметры оформления/отображения; числовой `bonus` также сохраняется.

Это подтверждает назначение ответа как списка партнёрских вариантов с кодом и числовым бонусом. Но оно **не доказывает**, что `bonus` — это сумма за просмотр видео или что именно этот ответ определяет серверное начисление `+0.69`.

### 3.4. Новая граница вывода

На клиенте теперь видны две связанные, но разные сущности:

1. `dailyTargetPartnerCode` — код партнёра, выбранный/отображаемый в состоянии ежедневной цели.
2. `PartnerResponse(code, bonus)` — список партнёров и их бонусных параметров, получаемый отдельным API.

Их связь с rewarded-video начислением не установлена. В частности, наличие кода партнёра `ad` и бонусного значения в конфигурации не позволяет вывести формулу `+0.69`.

## 4. Сводная схема подтверждённых потоков

```text
Rewarded video
  ├─ AppLovin MAX /2.0/mvr  (validation)
  ├─ AppLovin callback onUserRewarded
  │    └─ AdCoin p70 → v9(discriminator=1)
  │         └─ refBonus/get → g70.H (refPercent)
  ├─ AppLovin /2.0/mcr     (report)
  └─ Axon event=end        (video completion analytics)

AdCoin balance refresh
  ├─ POST /adcoin/updateData
  │    └─ response.cash → g70.D
  └─ GET /withdrawal/methods/get/{id}
       └─ response.balance → g70.D

Daily target / partner configuration
  ├─ UpdateDataResponse.dailyTargetPartnerCode
  │    └─ daily-target UI state
  ├─ UpdateDataResponse.adBonusDays
  │    └─ g70.p(...)
  └─ GET /adcoin/partners/get/{...}
       └─ List<PartnerResponse(code, bonus)> → partner UI model
```

Схема показывает найденные клиентские вызовы и связи. Она не изображает неизвестный серверный механизм начисления.

## 5. Что ещё не доказано

1. Какой именно backend endpoint или postback увеличивает AdCoin balance.
2. Есть ли в MAX dashboard активный S2S Rewarded Callback и как он настроен.
3. Принимает ли AdCoin решение о начислении по AppLovin callback, Axon `event=end`, по внутреннему server-side событию рекламной сети или по их комбинации.
4. Как рассчитывается `+0.69` и зависит ли сумма от рекламного источника, кампании, страны, процента бонуса или другой серверной конфигурации.
5. Что именно означает `PartnerResponse.bonus` в бизнес-логике backend и как он влияет на ежедневную цель.

## 6. Следующие направления исследования

1. Продолжить анализ всех call sites `s00.w0(...)` и связанных экранов: выяснить, когда загружается список партнёров и каким действием пользователь меняет `dailyTargetPartnerCode`.
2. Проверить, где `adBonusDays` отображается и какие условия влияют на его значение; не смешивать его с начислением за один ролик.
3. По новым сетевым дампам искать события, которые появляются между завершением видео и первым `updateData` с новым `cash`, сравнивая циклы с успешным и безуспешным начислением.
4. Искать конфигурацию MAX S2S callback и `custom_data`/placement только в безопасных метаданных, не публикуя ключи, токены, идентификаторы пользователя или рекламные идентификаторы.
5. Если клиентский APK не содержит endpoint начисления, зафиксировать это как предел доступной клиентской экспертизы, а не делать предположение о конкретном postback.

## 7. Итоговая оценка

Этапы 1–21 дали достаточно данных, чтобы **отделить подтверждённые клиентские действия от предположений о backend**. Мы знаем, что локальный MAX callback сам не начисляет `cash`, а запросы `updateData` и `withdrawal/methods/get` только отражают состояние сервера. Мы также наблюдали два увеличения баланса на `+0.69` после двух видеоциклов.

Главная нерешённая задача теперь узкая: найти серверную точку, которая связывает завершённый rewarded ad с изменением баланса. Дальнейшее повторное перечисление уже известных SDK callbacks мало что даст; приоритет — сопоставление дополнительных сетевых циклов и анализ конфигурации/серверных callback-механизмов.
