# AdCoin: поиск события, которое запускает серверное начисление

**Отчёт №23 · 26 ноября 2026**

## Краткий вывод

Самая сильная найденная версия: баланс за просмотр MAX Rewarded Video пополняется не прямым запросом из приложения AdCoin, а через **AppLovin MAX Server-to-Server (S2S) Rewarded Callback** — серверный GET-запрос от серверов AppLovin к URL, заданному в настройках rewarded ad unit в MAX Dashboard.

Это существенно сильнее прежней гипотезы «баланс вырос вскоре после `mcr` и Axon `event=end`». Документация AppLovin описывает отдельную сервер-серверную цепочку, которая не проходит через устройство. В APK найдено и необходимое связывание рекламного пользователя с внутренним ID AdCoin: приложение задаёт MAX `userIdentifier` равным внутреннему числовому ID пользователя.

**Ограничение доказательства:** APK и клиентский MITM не содержат настройки Server Side Callback URL из MAX Dashboard и не показывают запрос AppLovin-сервер → AdCoin-сервер. Поэтому можно уверенно назвать механизм, который лучше всего объясняет наблюдения, но пока нельзя утверждать, что конкретный AdCoin ad unit действительно настроен на этот callback, и нельзя назвать точный URL серверного обработчика.

## 1. Ключевая находка в APK: MAX получает внутренний ID пользователя AdCoin

Файл `apk_analysis/apktool/smali/p70.smali`, инициализация MAX:

1. Читается `g70.m`.
2. Значение преобразуется в строку.
3. Передаётся в `AppLovinSdkSettings.setUserIdentifier(...)`.

Это важно: в документации MAX `{USER_ID}` — publisher-defined user ID, который передаётся в S2S rewarded callback. То есть AdCoin явно связывает MAX-пользователя с внутренним аккаунтом AdCoin до показа рекламы.

Дополнительная деталь: общий builder AppLovin `com/applovin/impl/x6.smali` формирует поле `cuid` из SDK user identifier, если оно задано и соответствующий SDK-флаг включён. Это подтверждает, что внутренний идентификатор используется в коммуникации SDK с AppLovin. Поле `cuid` и S2S-макрос `{USER_ID}` — не одно и то же имя и не следует смешивать их, но оба берут начало из установленного user identifier.

## 2. Официальная серверная цепочка MAX

Документация AppLovin MAX S2S Rewarded Callback API описывает такую последовательность:

1. SDK определяет завершение rewarded-видео и выполняет клиентские процессы проверки.
2. SDK сообщает результат серверам AppLovin.
3. Уже сервер AppLovin отправляет HTTP(S) GET на Server Side Callback URL, заданный для rewarded ad unit.
4. Callback может содержать `{USER_ID}`, `{EVENT_ID}`, `{EVENT_TOKEN}`, `{AMOUNT}`, `{CURRENCY}`, `{AD_UNIT_ID}`, `{NETWORK_NAME}` и другие макросы.
5. Получатель проверяет подпись события через `EVENT_TOKEN` и Event Key. `EVENT_TOKEN` вычисляется как SHA-1 от `EVENT_ID + Event Key`.

Критически важно: AppLovin прямо указывает, что S2S callback **не проходит через устройство пользователя**. Это объясняет, почему мы не видим такой запрос в MITM дампе телефона.

Источники:
- AppLovin, S2S Rewarded Callback API: https://dash.applovin.com/documentation/mediation/s2s-rewarded-callback-api
- AppLovin, How server-to-server callback works: https://support.applovin.com/en/max/faq/how-server-to-server-callback-works

## 3. Как это соотносится с уже найденными событиями

| Событие | Направление | Что оно означает | Начисляет ли само по себе AdCoin баланс? |
|---|---|---|---|
| MAX `2.0/mvr` (`TaskValidateMaxReward`) | устройство → AppLovin | Запрос проверки/подготовки MAX reward | Не доказано; это не endpoint AdCoin |
| MAX `2.0/mcr` (`TaskReportMaxReward`) | устройство → AppLovin | Клиентский отчёт MAX о результате reward validation | Не доказано; это не endpoint AdCoin |
| Axon `event=end`, `pv=100` | устройство → Axon | Аналитическое событие завершения просмотра | Не доказано; это не endpoint AdCoin |
| MAX S2S Rewarded Callback | AppLovin сервер → заданный backend URL | Серверное подтверждение, что пользователь квалифицируется на награду | **Наиболее вероятный триггер серверного зачисления** |
| AdCoin `/adcoin/updateData` | устройство → AdCoin | Получение актуального `cash` и других данных | Нет: это синхронизация/чтение состояния |

Следовательно, прежняя временная корреляция `mcr`/Axon/`updateData` была лишь косвенной. Новая гипотеза объясняет, почему баланс появляется позже: между клиентским отчётом MAX и последующим чтением баланса может происходить невидимый устройству S2S callback и серверная запись в кошелёк.

## 4. Почему это лучше объясняет код AdCoin

- `p70.onUserRewarded(MaxAd, MaxReward)` не извлекает `MaxReward.amount` и не отправляет сумму в API AdCoin.
- Этот callback запускает отдельную ветку `refBonus/get`, которая обновляет реферальный процент, а не баланс.
- В клиентском API AdCoin не найден отдельный endpoint для claim/credit rewarded video.
- `updateData` принимает идентификаторы сессии/устройства/рекламы и возвращает `cash`; он не содержит в запросе event ID MAX или сумму reward.
- MAX user identifier установлен в значение внутреннего ID AdCoin — это как раз позволяет S2S обработчику сопоставить callback с аккаунтом.

В совокупности эти признаки делают S2S Rewarded Callback основной рабочей гипотезой.

## 5. Что именно пока не доказано

Не найдено:

1. Значение Server Side Callback URL, настроенного в MAX Dashboard для используемого rewarded ad unit.
2. Факт, что этот URL принадлежит AdCoin и какой у него path.
3. Запись входящего запроса S2S на сервере AdCoin.
4. Серверная проверка `EVENT_TOKEN` и `EVENT_ID`.
5. Точная серверная формула перевода MAX reward в `+0.69`.

Нельзя подменять эти пробелы догадкой о пути вроде `/reward/callback`: такой путь в APK не обнаружен, и выдумывать его нельзя.

## 6. Что даст окончательное доказательство

Достаточно получить один из следующих артефактов:

- **MAX Dashboard → rewarded ad unit → Server Side Callback URL**: подтвердит endpoint и используемые макросы;
- лог входящих запросов этого callback на backend AdCoin: покажет реальное событие, `EVENT_ID`, результат валидации и ответ обработчика;
- серверный журнал транзакций кошелька, где запись начисления связана с тем же `EVENT_ID` или callback request ID.

Самая сильная проверка — корреляция одного callback `EVENT_ID` с одной ledger-записью `+0.69`. Тогда причинная цепочка будет доказана, а не выведена по времени.

## 7. Следующая точка исследования в имеющихся материалах

В текущем ZIP нет MAX Dashboard export или backend logs. Поэтому дальнейшее ковыряние `updateData` и `withdrawal/methods/get` не раскроет невидимый S2S handler. Имеет смысл искать конфигурацию MAX ad unit / Server Side Callback URL и сопоставить её с серверным логом за один из уже зафиксированных rewarded-сеансов. Если доступа к Dashboard/backend нет, можно продолжить статический поиск доменов и ссылок AdCoin, но он не заменит доказательства входящего S2S запроса.

## Итоговая оценка

**Наиболее вероятное событие, запускающее начисление: AppLovin MAX S2S Rewarded Callback.**

**Уровень уверенности: высокий как архитектурная гипотеза; не окончательное подтверждение конкретной настройки AdCoin.**

Решающие основания: AppLovin документирует невидимый устройству S2S callback после проверки rewarded-видео; AdCoin устанавливает MAX `userIdentifier` в свой внутренний user ID; прямого клиентского вызова начисления в AdCoin API нет; баланс обновляется позднее отдельным запросом чтения.
